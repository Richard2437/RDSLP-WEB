1. DESCRIPCIÓN GENERAL
----------------------
RDSLP es una plataforma web educativa tipo red social enfocada en lenguajes
de programación. Permite a los usuarios registrarse, iniciar sesión, explorar
contenido de lógica, lenguajes, bases de datos y libros, además de interactuar
en un muro comunitario y participar en eventos.

La aplicación utiliza Supabase como Backend-as-a-Service (BaaS) para la
autenticación, base de datos PostgreSQL y Row Level Security (RLS).

2. PÁGINAS DEL SITIO
--------------------
  - login.html        → Inicio de sesión (email/contraseña + Google OAuth)
  - sesion.html        → Registro de nuevos usuarios con consentimiento legal
  - dashboard.html     → Panel principal (inicio, contenido, admin)
  - muro.html          → Muro de publicaciones con likes y comentarios
  - ejercicios.html    → Editor de ejercicios con ejecución de código en vivo
  - logica.html        → Contenido de lógica de programación
  - libros.html        → Biblioteca de libros recomendados
  - comunidad.html     → Salas y comunidades (públicas/privadas)
  - perfil.html        → Perfil del usuario
  - databases.html     → Sección de bases de datos

3. ARCHIVOS JAVASCRIPT PRINCIPALES
-----------------------------------
  - JS/supabase-client.js → Cliente oficial de Supabase para producción
                            (Auth, Google OAuth, perfiles en la nube)
  - JS/auth.js         → Autenticación, registro, login, roles, ban/unban
  - JS/dashboard.js    → Lógica del dashboard y panel de administración
  - JS/login.js        → Lógica del formulario de login
  - JS/sesion.js       → Lógica de registro y validación de Habeas Data
  - JS/legal.js        → Módulo legal de Términos de Servicio y Habeas Data
  - JS/comunidad.js    → Gestión de salas públicas y privadas
  - JS/ejercicios.js   → Editor de código con ejecución en sandbox
  - JS/muro.js         → Publicaciones y comentarios
  - JS/api-client.js   → Cliente API para conexión con backend serverless

4. FUNCIONES SERVERLESS (api/)
-------------------------------
  - api/config.js      → Expone variables de entorno públicas (Supabase URL
                          y Anon Key) de forma segura sin hardcodear en el frontend
  - api/auth.js        → Autenticación backend con JWT firmado
  - api/posts.js       → CRUD de publicaciones del muro
  - api/comments.js    → CRUD de comentarios
  - api/likes.js       → Sistema de likes

5. ROLES DE USUARIO
-------------------
  - admin      → Acceso total: gestionar usuarios, banear, cambiar roles
  - moderator  → Permisos intermedios de moderación
  - user       → Usuario estándar con permisos básicos
  - banned     → Cuenta suspendida: sin acceso a la plataforma

  Para asignar roles desde Supabase SQL Editor:
    SELECT public.asignar_rol('correo@ejemplo.com', 'admin');

6. ESTRUCTURA DE DATOS EN SUPABASE
------------------------------------
  Tabla: public.perfiles (sincronizada con auth.users vía trigger)
  {
    id:          UUID (referencia a auth.users.id),
    nombre:      TEXT (nombre completo del usuario),
    correo:      TEXT (correo electrónico),
    rol:         TEXT ('user' | 'moderator' | 'admin' | 'banned'),
    created_at:  TIMESTAMP WITH TIME ZONE
  }

  Políticas RLS:
  - Lectura pública para todos (anon + authenticated)
  - Inserción permitida para registros
  - Actualización permitida (roles gestionados desde funciones SECURITY DEFINER)

7. PRIVACIDAD DE COMUNIDADES Y SALAS
--------------------------------------
  a) Decisión de Privacidad por el Creador:
     - 🟢 PÚBLICO / ABIERTO: Cualquier usuario registrado puede descubrir la
       sala, inscribirse libremente y chatear.
     - 🔒 PRIVADO (CON INVITACIÓN): Protegida con código alfanumérico único
       (ej: RDSLP-ABC12). Solo acceden quienes ingresen el código correcto.
  b) Gestión de la Sala (Exclusivo Creador / Admin):
     - Cambiar privacidad en cualquier momento
     - Regenerar código de invitación con un clic
     - Modificar nombre y descripción
     - Compartir código por WhatsApp, Discord o correo
  c) Permisos Estrictos:
     - Verificación automática de autorización en cada sala
     - Bloqueo de acceso no autorizado a salas privadas

8. CUMPLIMIENTO LEGAL Y HABEAS DATA (LEY 1581 DE 2012)
-------------------------------------------------------
  a) Política de Tratamiento de Datos Personales (Habeas Data):
     - Módulo legal interactivo (JS/legal.js)
     - Derechos ARCO (Acceso, Rectificación, Cancelación, Oposición)
     - RDSLP NO vende ni cede datos a terceros con fines comerciales
  b) Términos y Condiciones de Servicio:
     - Reglas de convivencia, prohibición de código malicioso
     - Licenciamiento de código compartido para aprendizaje colaborativo
  c) Consentimiento Informado:
     - login.html: Aviso legal con enlaces a Términos y Habeas Data
     - sesion.html: Checkbox obligatorio con fecha ISO de aceptación

9. SEGURIDAD (DevSecOps)
-------------------------
  a) Gestión de Secretos:
     - Variables de entorno (.env) NUNCA se suben al repositorio (.gitignore)
     - Credenciales de Supabase se inyectan vía /api/config (endpoint serverless)
     - NO hay credenciales hardcodeadas en el código fuente del frontend
     - Las variables sensibles se configuran en el panel de Vercel
  b) Separación Cliente / Servidor:
     - Las claves públicas (Supabase URL y Anon Key) se sirven desde /api/config
     - Los secretos (JWT_SECRET) solo se usan en funciones serverless (api/)
  c) Row Level Security (RLS):
     - Todas las tablas de Supabase tienen RLS habilitado
     - Políticas de acceso por rol y autenticación
  d) Protección de la Base de Datos:
     - Las operaciones de cambio de rol usan funciones SECURITY DEFINER
     - Trigger automático sincroniza auth.users con la tabla perfiles
  e) Validaciones:
     - Validación de inputs en cliente y servidor
     - CORS configurado en funciones serverless
     - JWT firmado con secreto del lado del servidor
  f) .gitignore DevSecOps:
     - Excluye: .env, .env.*, certificados (*.pem, *.key, *.cert),
       archivos de IDE, archivos de base de datos local, logs

10. CONFIGURACIÓN DE GOOGLE OAUTH
-----------------------------------
  Para habilitar el login con Google:

  1. En Google Cloud Console (https://console.cloud.google.com):
     - Crear proyecto → APIs & Services → Credentials
     - Crear OAuth 2.0 Client ID (tipo: Web Application)
     - Agregar redirect URI:
       https://TU_PROJECT_ID.supabase.co/auth/v1/callback
     - Copiar Client ID y Client Secret

  2. En el Dashboard de Supabase:
     - Authentication → Providers → Google
     - Habilitar el toggle de Google
     - Pegar Client ID y Client Secret
     - Guardar

  Si NO se configura, aparecerá el error:
    {"code":400,"error_code":"validation_failed",
     "msg":"Unsupported provider: provider is not enabled"}

12. VARIABLES DE ENTORNO REQUERIDAS
-------------------------------------
  Configurar en Vercel → Settings → Environment Variables:

  | Variable           | Descripción                           |
  |---------------------|---------------------------------------|
  | SUPABASE_URL        | URL del proyecto Supabase             |
  | SUPABASE_ANON_KEY   | Clave pública (anon key) de Supabase  |
  | JWT_SECRET          | Secreto para firmar tokens JWT        |

  Para desarrollo local, crear archivo .env basado en .env.example

13. CÓMO EJECUTAR
------------------
  Desarrollo local:
    1. Copiar .env.example a .env y completar credenciales
    2. npm install (solo si necesitas dependencias adicionales)
    3. Abrir index.html directamente en el navegador
       o usar un servidor local (ej: npx serve .)

  Producción (Vercel):
    1. Conectar repositorio en Vercel
    2. Configurar variables de entorno en Vercel
    3. Desplegar automáticamente
